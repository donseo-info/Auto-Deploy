# Анализ проекта Auto-Deploy

Дата анализа: 2026-08-24 · Ревизия: `ade2d8a` («Релиз»)

---

## 1. Что это

Одностраничный PHP-инсталлятор, который настраивает автодеплой с GitHub на shell-хостинг
через webhook. Заливается на сервер, открывается в браузере, проводит пользователя по
5 шагам и на выходе создаёт рядом с собой `deploy.php` — приёмник вебхуков GitHub.

**Состав репозитория:**

| Файл | Размер | Назначение |
|---|---|---|
| `installer.php` | 942 строки, 27 КБ | Всё приложение: логика + CSS + HTML в одном файле |
| `._installer.php` | 4 КБ | Мусорный AppleDouble-файл macOS, попал в репозиторий по ошибке |

Больше в проекте нет ничего: ни README, ни `.gitignore`, ни лицензии, ни тестов, ни CI.
История — 5 коммитов, один автор, ветки `main` и рабочая.

**Стек:** чистый PHP (без зависимостей и Composer), сессии, `shell_exec`, вручную
написанный CSS (тёмная тема, JetBrains Mono + Unbounded с Google Fonts), капля JS для
копирования команд в буфер.

## 2. Как работает

**Шаг 1 — Проверка окружения** (`check_env`): текущая папка, `whoami`, доступность
`shell_exec`, наличие `git`, права на запись.

**Шаг 2 — Репозиторий** (`check_repo` / `init_repo`): пользователь вводит URL репозитория,
папку проекта и ветку. Проверяется наличие `.git`, текущая ветка, remote, пробный
`git fetch`. Если репозитория нет — кнопка «Инициализировать»: `git init` →
`git remote add origin` → `git fetch` → `git checkout` → `git reset --hard`.

**Шаг 3 — Генерация** (`generate_deploy`): секрет берётся из формы или генерируется
(`bin2hex(random_bytes(16))`), в текущую папку пишется `deploy.php`.

**Шаг 4 — Инструкция**: показывает Payload URL и Secret, объясняет настройку вебхука на
GitHub. Кнопка ручного теста деплоя.

**Шаг 5 — Готово**: лог теста и напоминание удалить инсталлятор.

**Сгенерированный `deploy.php`** читает тело запроса, сверяет `X-Hub-Signature-256` через
`hash_hmac` + `hash_equals`, проверяет что `ref` равен целевой ветке, выполняет
`git fetch origin` и `git reset --hard origin/<branch>`, пишет всё в `deploy.log`.

Внизу каждой страницы — шпаргалка по git на 4 раздела с копированием по клику.

---

## 3. Сильные стороны

- **Ноль зависимостей, один файл.** Для «залил по FTP на шаред-хостинг и открыл» это
  правильная архитектура, а не недостаток.
- **Проверка подписи вебхука сделана корректно**: HMAC-SHA256 + `hash_equals`
  (constant-time), это именно то, что рекомендует GitHub. Многие самописные деплоеры
  здесь ошибаются.
- **Диагностика перед настройкой** — сильная идея. Хостинги часто режут `shell_exec`,
  и инсталлятор честно об этом сообщает вместо загадочной ошибки потом.
- **Пошаговый мастер с состоянием в сессии** — понятный UX, состояние переживает
  перезагрузку страницы.
- `escapeshellarg` применяется к путям (13 мест) — про экранирование автор в целом знает.
- Вывод в HTML везде проходит через `htmlspecialchars` — XSS в интерфейсе не нашёл.
- Аккуратный, читаемый интерфейс; шпаргалка по git — приятный практичный бонус.

## 4. Безопасность

Это главная проблемная зона. Инструмент по своей природе выполняет shell-команды от лица
веб-сервера, поэтому цена ошибки здесь максимальная.

### 4.1 КРИТИЧНО — нет никакой аутентификации

`installer.php` не защищён ничем: ни паролем, ни токеном в URL, ни ограничением по IP.
Любой, кто узнает или переберёт имя файла, получает полный доступ к мастеру, а значит —
возможность выполнять команды на сервере (см. ниже), переписать содержимое папки сайта
и создать `deploy.php` со своим секретом.

Шаг 5 советует удалить инсталлятор после настройки, и это смягчает риск, но не убирает:
опасно всё окно от заливки до удаления, а про удаление регулярно забывают.

**Что делать:** обязательный пароль/токен при первом запуске (например, случайный токен,
который печатается в имя файла или требуется ввести из отдельно созданного файла на
сервере), плюс самоудаление инсталлятора после шага 5.

### 4.2 КРИТИЧНО — инъекция команд через поле «Ветка»

Путь экранируется, а ветка подставляется в shell-строку как есть:

```php
// installer.php:144, 151, 287
shell("cd " . escapeshellarg($dir) . " && git checkout -b {$branch} origin/{$branch}");
shell("cd " . escapeshellarg($dir) . " && git reset --hard origin/{$branch}");
```

Значение `main; <любая команда>` в поле «Ветка» выполнится на сервере. Затрагивает
`init_repo()` и `test_deploy` — оба доступны без аутентификации.

**Что делать:** `escapeshellarg($branch)` во всех трёх местах + валидация по
белому списку `^[A-Za-z0-9._\/-]+$`.

### 4.3 КРИТИЧНО — инъекция PHP-кода в генерируемый `deploy.php`

`generate_deploy()` подставляет `$secret`, `$dir` и `$branch` в исходник heredoc'ом без
экранирования кавычек. Проверено практически — секрет вида

```
abc'); system($_GET['c']); //
```

даёт синтаксически валидный файл:

```php
define('SECRET',      'abc'); system($_GET['c']); //');
```

То есть на сервере остаётся постоянный бэкдор в файле, который пользователю прямо
рекомендовано **не** удалять.

**Что делать:** `var_export($secret, true)` вместо интерполяции для всех трёх значений;
секрет дополнительно валидировать (hex/base64, разумная длина).

### 4.4 ВЫСОКО — `.git` и `deploy.log` оказываются в вебруте

Дефолтная папка проекта — `__DIR__`, то есть публичная директория сайта. После настройки
там лежат `.git/` (весь исходный код, история и, если репозиторий подключён по HTTPS с
токеном, — сам токен в `.git/config`) и `deploy.log` с путями сервера и выводом git.
Оба доступны по прямому URL.

**Что делать:** генерировать рядом `.htaccess`/подсказку для nginx, закрывающие `.git` и
`*.log`; лог по возможности писать выше вебрута.

### 4.5 СРЕДНЕ — токен репозитория утекает в интерфейс

`check_repo()` показывает результат `git remote get-url origin` как есть. Для приватного
репозитория формата `https://user:token@github.com/...` токен выводится на страницу и
попадает в историю браузера/скриншоты. Стоит маскировать credentials в выводе.

### 4.6 СРЕДНЕ — нет CSRF-защиты и нет серверной проверки шагов

Формы не содержат токена, а обработчики действий не проверяют, на каком шаге находится
пользователь: можно сразу отправить `generate_deploy` или `test_deploy`, минуя проверки.
При наличии аутентификации (4.1) это становится реальным вектором CSRF.

### 4.7 НИЗКО — логирование до проверки подписи

`deploy.php` пишет «Webhook получен» ещё до валидации сигнатуры — неаутентифицированный
запрос может неограниченно раздувать лог. `$ref` из payload попадает в лог без очистки
(инъекция переводов строк в лог).

## 5. Надёжность и функциональные пробелы

**Потеря данных при инициализации.** `init_repo()` делает `git init` + `git reset --hard`
в папке, где уже может лежать работающий сайт, — без бэкапа и без подтверждения. Файлы,
конфликтующие с репозиторием, будут перезаписаны молча. Нужен явный экран подтверждения и
проверка, что папка пуста либо пользователь согласился.

**Приватные репозитории подвешивают запрос.** При HTTPS-доступе к приватному репозиторию
git попытается спросить логин/пароль в терминале — процесс зависнет до таймаута PHP.
Лечится `GIT_TERMINAL_PROMPT=0` и `GIT_SSH_COMMAND='ssh -o BatchMode=yes'` в окружении
всех вызовов, плюс отдельный шаг мастера про deploy key / SSH-ключ, которого сейчас нет
вообще — это, пожалуй, главный функциональный пробел для реального применения.

**Нет таймаутов.** `git fetch` вызывается синхронно на шагах 2 и 4; при недоступной сети
страница висит до `max_execution_time` и отдаёт 504 без внятного сообщения.

**Некорректный Payload URL.** Строится как
`dirname($_SERVER['REQUEST_URI'])`, поэтому ломается при заходе с query-строкой
(например, после `?reset=1`) и при обращении к директории. Нужен `parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH)`
и учёт `X-Forwarded-Proto` — иначе за балансировщиком генерируется `http://` вместо `https://`.

**Деплой неполон.** `git reset --hard` не удаляет лишние untracked-файлы (нет
`git clean -fd`), не трогает submodules, не запускает `composer install`, миграции или
сброс кеша, не имеет хуков «до/после». Одновременные вебхуки не сериализуются — нет
файловой блокировки, два быстрых пуша могут наложиться друг на друга.

**Нет отката.** Неудачный деплой оставляет сайт в сломанном состоянии; ни релизных
директорий, ни фиксации предыдущего коммита для отката не предусмотрено.

**Возврат назад по шагам невозможен.** `next_step` только инкрементирует, сброс — только
недокументированным `?reset` в URL. Кнопки «Назад» в интерфейсе нет.

## 6. Совместимость

Код использует `str_contains()` (PHP 8.0+), стрелочные функции (7.4+) и `?:`-цепочки.
Проверки версии нет — на PHP 7.x, который до сих пор встречается ровно на тех дешёвых
шаред-хостингах, куда такой инсталлятор и заливают, файл упадёт с fatal error ещё до
первой строки интерфейса. Нужен ранний guard:

```php
if (PHP_VERSION_ID < 80000) { die('Требуется PHP 8.0+'); }
```

Отдельно: `shell_exec()` возвращает `null`, если функция отключена в `disable_functions`.
Результат сразу передаётся в `trim()` и `str_contains()` — на PHP 8.1+ это deprecation-
предупреждения, которые при `display_errors=On` попадут прямо в вёрстку. Стоит привести
результат к строке в самой функции `shell()`.

## 7. Код и репозиторий

- **942 строки в одном файле** — для самодостаточного инсталлятора приемлемо, но ~510
  строк из них это CSS. Логика (строки 1–290) читается хорошо: короткие функции,
  единый формат результата `['status','msg']`, никаких сюрпризов.
- **Дублирование**: блок отрисовки результатов проверок повторён дословно в шагах 1 и 2 —
  просится в функцию `render_checks($data)`.
- **Мёртвый код**: константа `CONFIG_FILE` определена и нигде не используется.
- **`._installer.php`** — служебный файл macOS в репозитории. Удалить и добавить
  `.gitignore` с `._*`, `.DS_Store`, а также `deploy.php`, `deploy.log`, `.deploy_config.php`.
- **Нет README** — для инструмента, который распространяется как «скачай и залей»,
  отсутствие инструкции и списка требований (PHP 8.0+, shell_exec, git, доступ к GitHub)
  это заметный пробел.
- **Коммиты** («Авто деплоер», «Фиксы ошибок», «Финал», «Релиз») не описывают изменения;
  первый коммит добавляет пустой файл. Нет тегов версий, хотя в коде есть
  `INSTALLER_VERSION`.

## 8. Приоритетный план

**Сначала — безопасность (без этого инструмент нельзя рекомендовать к использованию):**

1. Экранировать `$branch` в трёх shell-вызовах + валидация формата ветки (§4.2)
2. `var_export()` при генерации `deploy.php` + валидация секрета (§4.3)
3. Аутентификация инсталлятора и самоудаление после шага 5 (§4.1)
4. Генерация `.htaccess`, закрывающего `.git` и `*.log` (§4.4)

**Затем — работоспособность в реальных условиях:**

5. Guard на версию PHP и защита от отключённого `shell_exec` (§6)
6. `GIT_TERMINAL_PROMPT=0` + шаг настройки SSH/deploy key для приватных репозиториев (§5)
7. Подтверждение перед `git reset --hard` в непустой папке (§5)
8. Корректный Payload URL: `parse_url` + `X-Forwarded-Proto` (§5)

**Потом — качество:**

9. `git clean -fd`, файловая блокировка и хуки «после деплоя» в `deploy.php`
10. CSRF-токен и серверная проверка текущего шага
11. README, `.gitignore`, удаление `._installer.php` и `CONFIG_FILE`
12. Вынести повторяющийся рендер проверок в функцию

## Итог

Идея и UX хорошие, проверка подписи вебхука сделана правильно, диагностика окружения —
удачное решение. Но в текущем виде это инструмент, который сам создаёт уязвимость на
сервере: незащищённая страница с двумя способами выполнить произвольный код (инъекция в
ветку и инъекция в генерируемый `deploy.php`), плюс `.git` и лог, выложенные в публичный
доступ. Пункты 1–4 плана — обязательный минимум перед любым использованием на боевом
хостинге.
